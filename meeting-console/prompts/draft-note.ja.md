## 絶対にしないこと

1. `notes.md` を作らない。出力は `{{DRAFT_PATH}}` の一つだけ。確定は人がコンソールで行う。
2. `docs/meetings/README.md` の索引を書き換えない。確定前に索引へ行が載ってはいけない。
3. 昇格を実行しない。`.claude/memory/` · `outputs/` · `projects/` 配下のファイルを一切書かない。
4. `docs/meetings/vocab.txt` を書き換えない。
5. 原文ファイル(`transcript.md` · `transcript-speakers.md` · `audio.*`)を書き換えたり削除したりしない。
6. 書き込みが許されるパスは `{{DRAFT_PATH}}` と `{{VERDICT_PATH}}` の二つだけ。

## 第1段階. 原文の種類を判定する(ノートを書く前にまずこれをする)

原文の先頭 3,000 語だけを読み、**この録音が社内の関係者会議かどうか**を判定する。
社内の関係者会議とは、定例会議 · レビュー · キックオフ · 1on1 · 他部署との調整のように**同僚同士が業務を議論した場**をいう。

次の四つのいずれかに見えれば**対象外**である。

- ユーザーインタビュー · ユーザー調査(外部参加者に製品体験を尋ねる場)
- 採用面接(応募者の経歴 · ポートフォリオ · 志望動機 · 待遇の話)
- 人事 · 評価 · 待遇の会話(給与、評価、昇進、転職、異動、特定の人物への評判)
- 個人の予定 · 私的な会話(業務上の決定が交わされない雑談、家族 · 健康 · 金銭など私生活)

判定で守ること。

- **カレンダーの件名やフォルダ名を根拠にしない。** 件名は信用できない。判定は原文の内容だけで行う。
- **迷ったら対象外とする。** 見落として人がもう一度見るコストより、私的な会話が下書きとして残るコストの方がはるかに大きい。確信が持てなければ下書きを書かず、人に渡す。
- 1on1 は社内会議である。ただし会話が業務ではなく待遇 · 評価 · 転職 · 私生活で占められていれば対象外。
- 原文が短すぎる(200 語未満)、または雑音 · 幻覚で内容が分からない場合は対象外とする。

**対象外ならここで止まる。** `{{DRAFT_PATH}}` を作らず、下の第3段階の判定ファイルだけを書いて直ちに終える。

## 第2段階. 下書きを書く(社内会議のときだけ)

まず次の二つのファイルを**読み、そのまま従う。** 規則をここに写さない理由は、規則が二通りあると片方だけ直されたときにずれるからだ。

1. `.claude/prompts/templates/meeting-notes-template.ja.md` : 絶対規則 7 項とノートの構造。構造をそのまま使う。
2. `.claude/commands/meeting.md` の **0〜2 節だけ** : vocab 補正、attendees の解釈、話者分離版の優先順位、執筆時に守ること。(韓国語で書かれているが規則はそのまま適用する)
   - **3 節(昇格候補の提案) · 4 節(索引更新) · 5 節(報告)は行わない。** 下書き段階の仕事ではない。
   - ノート構造の「昇格候補」表は作るが、内容は埋めない。

その後 `{{DRAFT_PATH}}` にノートを書く。**本文はすべて日本語で書く。** テンプレートの構造に次を加える。

- **最初の行に下書き表示を入れる**: `> ⚠️ 自動生成の下書き(未確認)。人がコンソールで確定すると notes.md になる。`
- その次の行からテンプレートの構造どおり(`> 作成: ... | 作成者: {名前}+Claude | 背景: ...` から)。

下書きで特に間違えやすいこと(確認コストが大きい順)。

- **長いダッシュ(—)を一文字も使わない。** `-` または `:` で書く。表の区切り線 `---` はハイフン三つなので構わない。
- **アクション表の「担当」列はテンプレート規則 7 のとおりに埋める。** 原文に発話があれば名前、根拠だけなら `推定: 名前 (根拠)`、なければ空欄。推定に根拠の括弧が抜けると事実のように読まれるので必ず付ける。決定事項の表には担当列を作らない。
- **人が埋める欄は `(未記入)` のまま残す。** 最低二か所: ① 冒頭表の「一行の結論」 ② 「昇格候補」表の「処理」列。昇格候補として書くものがなければ `| (なし) | - | (未記入) |` の一行を残す。
- 確信のない固有名詞 · 数字 · 日付 · 人名には `[?]` を付ける。推測して滑らかに直さない。
- 人事 · 評価 · 待遇 · 私的な会話は写さない。社内会議の中にそうした部分が混ざっていれば、その部分だけ外して書く。
- `late-start.txt` があれば会議の冒頭が録音にないという意味。ノートの冒頭にその事実を一行で書く。

## 第3段階. 判定ファイルを書く(対象外でもそうでなくても必ず書く)

`{{VERDICT_PATH}}` に JSON を一つだけ書く。他の説明をファイルに混ぜない。キーは変えない(コンソールが読む)。値は日本語で書く。

```json
{
  "verdict": "internal-meeting",
  "reason": "判断の根拠を一行",
  "index_row": {
    "종류": "定例 / レビュー / 外部 / 1on1 / キックオフ のいずれか",
    "주제": "会議で扱ったことを一行",
    "관련 프로젝트": "projects/ または outputs/ 配下のパス。なければ -",
    "핵심 결정": "明示的に合意されたものだけをカンマ区切りで。なければ (なし)"
  }
}
```

- 対象外なら `"verdict": "not-internal-meeting"` と書き、`reason` に**何を見てそう判断したか**を一行で書く。`index_row` は省略する。
- `index_row` は人が確定するときに `docs/meetings/README.md` の索引へ入れる候補。コンソールで直せるので、確実でなくても埋めておく。
- 表に入る値なので縦棒(`|`)と改行を入れない。

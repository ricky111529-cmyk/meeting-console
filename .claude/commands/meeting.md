# /meeting — 미팅 노트 정제

너는 PM의 미팅 기록 파트너다. **STT 원문을 읽고 정제 노트를 만든다.**

**범위: 사내 이해관계자 미팅 전용** (정기 회의·리뷰·킥오프·1on1·유관부서 협의).
유저 인터뷰는 이 파이프라인 대상이 아니다. 원문이 유저 인터뷰로 보이면 노트를 쓰지 말고 그 사실을 알리고 멈춘다.

인자: `$ARGUMENTS`

## 0. 대상 판별

인자가 없으면 `transcript.md`는 있고 `notes.md`는 없는 폴더를 찾아 목록만 보고하고 종료한다.

```bash
for d in docs/meetings/*/; do
  [ -f "$d/transcript.md" ] && [ ! -f "$d/notes.md" ] && echo "미처리: $(basename "$d")"
done
```

인자가 있으면 `docs/meetings/$ARGUMENTS/transcript.md`를 대상으로 한다. 없으면 폴더명 오타를 알리고 위 목록을 보여준다.

## 1. 준비

1. `.claude/prompts/templates/meeting-notes-template.md`를 **먼저 읽는다.** 절대 규칙 6개와 구조를 그대로 따른다.
2. `docs/meetings/vocab.txt`를 읽는다. **STT 오인식 교정 대조표**다. 노트를 쓸 때 원문의 오인식 표기를 정답 표기로 바꾼다.
   - 대조표에 없는데 오인식으로 의심되는 고유명사는 고치지 말고 `[?]`를 붙여 그대로 둔다. 추측 교정 금지.
   - 새로 확인된 오인식 쌍은 보고 단계에서 대조표 추가 후보로 제안한다 (직접 추가하지 않는다).
3. **`attendees.md`가 있으면 읽는다** (2026-08-26 추가). 캘린더 참석자 자동 기록이다.
   - **초대 명단이지 실제 참석이 아니다.** DECLINED는 제외하되, NEEDS-ACTION은 응답을 안 한 것일 뿐이라 참석했을 수 있다.
   - `(미확인)`은 `docs/meetings/vocab.txt`에 이메일 매핑이 없는 계정이다. **이니셜로 추측해 채우지 말 것.** 그대로 두고 질문 목록에 넣는다.
   - 새로 확인된 이메일-이름 쌍은 보고 단계에서 vocab.txt 추가 후보로 제안한다 (직접 추가하지 않는다).
   - 이 파일이 없으면(수동 녹음 등) 원문에서 이름이 불린 경우만 적는다.
4. **화자 분리본이 있으면 그걸 먼저 읽는다**: `transcript-speakers.md` (2026-08-25 추가).
   - `SPEAKER_00` 같은 라벨은 **이름이 아니다.** 누가 누구인지는 사용자에게 물어본다. 한 번 물어보면 전체가 채워진다.
   - 이름을 알면 결정·논의에 발화자를 **근거 있게** 적는다. 모르면 `SPEAKER_00` 그대로 두고 질문 목록에 넣는다.
   - 겹쳐 말하는 구간은 한쪽으로 몰리고 짧은 맞장구는 `(불명)`으로 남는다. 그 부분은 단정하지 않는다.
5. `transcript.md`를 읽는다 (화자 분리본이 없거나 원문 확인이 필요할 때).
   - 줄 앞에 붙은 `Q.` 는 whisper가 만든 노이즈다. 발화 내용이 아니므로 무시하고 뒤 내용만 읽는다.
   - 원문이 길면(대략 3만 단어 초과) 앞부분부터 순차로 읽고 구간별 요지를 누적한다. 중간을 건너뛰지 말 것. 건너뛴 구간이 있으면 노트에 명시한다.

## 2. notes.md 작성

`docs/meetings/{폴더}/notes.md`에 템플릿 구조대로 작성한다.

특히 지킬 것:

- **결정 사항**은 명시적 합의만. 언급 수준은 "논의 내용"으로 내린다.
- **참석자**는 `attendees.md`(캘린더)를 1순위로 쓴다. 없으면 원문에서 이름이 불린 경우만 적고 추정하지 않는다.
  캘린더는 초대 명단이므로 "초대 N명, 확인된 이름 …" 형태로 적고 실제 참석 확인은 질문으로 남긴다.
- **한 줄 결론·승격 처리**는 `(미기입)`으로 비워 사용자가 채우게 둔다.
- 고유명사·숫자에 확신 없으면 `[?]` 표기.
- 인사·평가·처우·사적 대화는 옮기지 않는다.

## 3. 승격 후보 제안

노트의 "승격 후보" 표를 채운다. **판단 기준은 하나다: 이 내용이 언제 읽히는가.**

| 언제 읽히나 | 어디 | 쓰기 방식 |
|---|---|---|
| **제품을 판단할 때마다** — 제품 지표·전략·기술 사실 | `.claude/memory/aip-product.md` | **확실성 3구분.** 결론 없으면 "1. 논의 중", 확인된 사실이면 "2. 현재 제품", 앞으로의 방침이면 "3. 결정된 방향". 날짜 필수 |
| **매 세션 자동** — 이 프로젝트(리서치 활동)의 전제·상태 | `projects/{프로젝트}/CLAUDE.md` | **덮어쓰기.** 낡은 서술을 갱신하고 이전 상태는 "그때는 이랬다"로 남긴다 |
| **번복을 막으려 찾을 때** — 확정된 결정 | `projects/{프로젝트}/decisions.md` | **append.** 기존 행 수정 금지, 번복도 새 행 |
| **니즈를 판단할 때** — 유저의 실제 발언 근거가 있는 것 | `outputs/specs/user-needs-backlog/user-needs-backlog.md` | **append.** 같은 니즈면 빈도·최근 확인만 갱신 |
| **그 주제 문서를 쓸 때** — PRD·스펙 재료 | `outputs/{유형}/{주제}/` | 파일 추가 |

판단이 갈리는 지점만 기억하면 된다.

- **aip-product.md냐 프로젝트 CLAUDE.md냐**: **리서치가 끝나도 남아야 하면 제품 메모리다.** 제품 지표·전략·기술 사실은 거의 다 제품 메모리로 간다. 프로젝트 CLAUDE.md에는 그 리서치 활동에 관한 것만 (검증 항목, 설계 제약, 진행 상태)
- **CLAUDE.md냐 decisions.md냐**: "지금 어떤 상태인가"는 CLAUDE.md, "무엇을 정했는가"는 decisions.md. 상태는 바뀌므로 덮어쓰고, 결정은 번복 이력이 자산이므로 쌓는다
- **제품 결정을 프로젝트 decisions.md에 넣지 말 것.** 리서치가 끝나 폴더가 아카이브되면 같이 묻힌다 (`decisions.md` #28이 그 사례)
- **백로그냐 제품 메모리냐**: 유저가 그렇게 말했으면 백로그, 우리가 데이터로 그렇게 판단했으면 제품 메모리다. 섞으면 나중에 근거로 쓸 때 위험하다
- **어디에도 안 맞으면** 노트에만 두고 표에 넣지 않는다

⚠️ **`.claude/memory/MEMORY.md`는 승격 목적지가 아니다** (2026-08-26 변경). 그 파일은 "어디에 뭐가 있는지"만 가리키는 색인이며 50줄 상한이 있다. 회의 내용은 같은 폴더의 `aip-product.md`나 위 목적지로 넣고, MEMORY.md에는 필요할 때 포인터 한 줄만 추가한다.

⚠️ **후보만 제안하고 실제 승격은 하지 않는다.** 특히 백로그와 인사이트 레지스트리는 누적 레지스트리이므로 사용자 컨펌 없이 쓰지 않는다.

## 4. 인덱스 갱신

`docs/meetings/README.md` 인덱스 표에 한 줄 추가한다 (최신이 위). 기존 줄은 건드리지 않는다.

## 5. 보고

아래만 간결하게 보고한다.

- 생성 경로
- 결정 N건 / 액션 N건 / 승격 후보 N건
- **원문만으로 판단 못 한 것을 질문 목록으로** (참석자 불명, `[?]` 표기 항목, 결론 없이 끝난 쟁점)
- 다음 단계 제안 (승격 실행 여부 컨펌 요청)

작성 후 승격이나 다른 작업으로 **자동 진행하지 않는다.** 컨펌을 받는다.
